# 《GEO 内容评估》建议 8 落地说明

> 日期：2026-07-29  
> 状态：方案确认稿，尚未开发完成或上线

## 原建议说了什么

《GEO 内容评估》的建议 8 是：

> 把平台维度接进生文链路。

文档指出的现状是：

- 后端查询提示词模板时，本来支持按平台筛选。
- 现有生文 Loop 只查询“生文模板”，没有说明文章要发到哪个平台。
- Verifier 也暂时忽略了平台维度。

直接后果是：

- Writer 写作时不知道文章最终发到哪里。
- 可能使用不适合目标平台的模板。
- Writer 和 Verifier 不知道平台的硬性要求。
- 格式问题往往到发布阶段才暴露。

原文同时说明，建议 8 和建议 4 的“平台参数表”是一件事的两面，应该一起做：

- 建议 8 负责把平台传进写作、审核和保存流程。
- 建议 4 负责沉淀每个平台的规则。

## 我们确认的落地方向

核心目标是：

> 在开始写作前确定目标平台，并让模板选择、Writer、Verifier、文章保存和发布检查使用同一个平台及同一套平台规则。

平台和平台规则不写死在后端代码或 Skill 中，而是存进数据库，由 MCP 提供给正式 GEO Skill。

## 一、数据库会增加什么

### 1. 内容平台

数据库增加内容平台配置，例如：

- 头条
- 小红书
- 公众号

用户可以在页面中新增、修改和停用平台。

以后新增一个内容平台，不需要再修改 Skill 中的平台清单。

需要注意：

> 新增内容平台只代表 GEO 可以为它写文章，不代表已经支持自动发布到该平台。自动发布仍需要单独接入发布工具。

### 2. 平台规则

每个平台可以维护自己的规则，例如：

- 标题字数限制
- 正文字数要求
- 图片格式和尺寸
- 外链、二维码要求
- 推荐的标题方式
- 推荐的篇幅和配图数量

规则分为两类：

- 硬规则：不满足就不能保存或发布。
- 软偏好：用于指导 Writer 和 Verifier，不直接阻止发布。

规则会记录版本、来源和日期。以后从一次发布失败中学到新要求时，可以形成一个新规则版本，而不是只修改那一篇失败文章。

### 3. 文章目标平台

文章增加“目标平台”字段，用来说明：

> 这篇文章当前是为哪个平台准备的？

历史文章不自动猜测平台，统一保持“未指定”。

新生文文章由 MCP 或 Pipeline 自动填写目标平台。

文章列表和详情页会显示目标平台，用户也可以人工修改。人工修改后，文章需要按照新平台规则重新审核。

### 4. 新文章生成留痕

从新版生文链路启用后，系统开始记录新 AI 文章当时使用的：

- 模板
- 模板当时的正文
- 实际交给 Writer 的提示词
- 平台规则版本
- 问题和模型

这部分由 `article_generation_contexts` 保存。

它不是建议 8 的核心要求，而是我们针对“以后怎么确认一篇文章用了什么模板和提示词”增加的补充能力。

历史文章不补造这些信息。

## 二、MCP 会改变什么

### 新增平台列表工具

正式 Skill 通过 MCP 查询当前启用的平台、名称和别名。

Skill 不再写死“头条、小红书、公众号”等平台清单。

### 新增平台规则工具

正式 Skill 通过 MCP 查询目标平台当前生效的规则。

平台规则只维护在数据库，不复制到 Skill 中。

这样可以避免：

- 数据库规则已经更新，但 Skill 仍使用旧规则。
- Writer、Verifier 和后端各维护一套不同规则。

### 模板查询增加平台

生成头条文章时，只返回：

- 头条专属模板
- 通用模板

不会返回小红书专属模板。

### 保存文章时携带平台

新版 `save_article` 会携带：

- 目标平台
- 使用的平台规则版本
- 使用的模板和提示词信息

后端保存前会再次确认模板、平台和规则相互匹配。

### 文章和参考查询增加平台筛选

- 今日生文结果可以按平台分别统计。
- 质量参考可以按平台筛选。
- 同平台参考不足时明确提示，不用其他平台文章冒充同平台参考。

## 三、正式 GEO Skill 会改变什么

正式 GEO Skill 的新流程是：

1. 根据用户要求确定目标平台；没有指定时读取数据库中的默认平台。
2. 通过 MCP 查询目标平台规则。
3. 通过 MCP 查询该平台可用的生文模板。
4. Writer 按平台规则写作。
5. Verifier 按同一套规则审核。
6. 保存文章时写入目标平台和生成留痕。

Skill 不再保存固定的平台清单，也不保存平台规则正文。

只修改正式插件仓库中的 Skill，不再修改 GEO 仓库内已经废弃的 fallback Skill。

## 四、前端会看到什么

### 平台与规则管理

普通登录用户可以：

- 新增、修改和停用内容平台。
- 为平台创建和更新规则版本。
- 查看规则来源和更新时间。

### 文章平台展示

文章列表和详情显示：

- 当前目标平台
- 未指定平台

用户可以人工修改文章平台。

如果文章最初按头条生成，后来改成小红书，详情页会区分：

- 当前目标平台：小红书
- 生成时平台：头条

原来的生成记录不会被覆盖。

## 五、历史数据怎么处理

本次不猜测历史数据：

- 历史文章目标平台保持“未指定”。
- 历史文章不补模板正文和提示词。
- 现有模板保持“通用”，以后由用户逐步标记平台。
- 旧生文调用在兼容期内继续可用。

从新版生文链路上线后，才开始积累可信的平台和生成记录。

## 六、这项改动的价值

### 写作前发现问题

平台格式问题不必等到发布时才发现。

### 避免模板错用

头条文章不会再拿到小红书专属模板。

### Writer 和 Verifier 标准一致

两者使用数据库中同一版本的平台规则。

### 平台经验可以沉淀

一次发布失败学到的新规则，可以进入平台规则库，避免同一个错误重复发生。

### 文章可以复盘

新文章可以说明当时使用了哪个平台、模板、提示词和规则版本。

## 本期不包括

- 不自动判断历史文章属于哪个平台。
- 不自动修改历史模板的平台归属。
- 不因为新增内容平台就自动获得发布能力。
- 不记录每一次失败的模型调用。
- 不建设一篇文章自动生成多个平台版本的能力。

## 最终结果

建议 8 落地后，生文链路将从：

```text
选一个生文模板 → 写文章 → 审核 → 发布时才发现平台问题
```

变为：

```text
确定平台
→ 读取平台规则
→ 选择该平台或通用模板
→ Writer 按规则写
→ Verifier 按同一规则审
→ 后端再次检查并保存
→ 发布前按最新规则复查
```

这份方案的重点不是增加更多提示词，而是让平台要求成为一份可维护、可复用、可沉淀的业务数据，并贯穿文章生成全过程。
